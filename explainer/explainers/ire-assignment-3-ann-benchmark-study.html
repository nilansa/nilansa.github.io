Benchmarking Approximate Nearest Neighbour Search

You have one million stored vectors. A new query arrives. Must you compare it with every vector, or can you search only the promising ones? This assignment makes you measure the accuracy, time, and memory cost of answering that question.

01 · Start here

What is the assignment trying to find?

Imagine a warehouse with 1,000,000 items. Each item has a numerical description. A customer asks for the 10 most similar items.

Exact search

Inspect every item and return the true closest 10. Correct, but potentially expensive when the warehouse grows.

FAISS IndexFlatL2

Approximate search (ANN)

Use a shortcut to inspect fewer items. Usually faster, but it may miss some of the true closest 10.

HNSW · IVF-Flat · IVF-PQ

Central trade-off: Search quality (recall@10) versus search speed (queries per second), with index memory and construction time as additional costs.
02 · Basic technical words

Vectors, nearest neighbours, and distance

A vector is an ordered list of numbers. Its dimension is the number of entries. For example, A = [1, 2] is a 2-dimensional vector. In this assignment SIFT vectors have 128 dimensions and GloVe vectors have 100.

A query vector describes what we seek. A nearest neighbour is a stored vector with the smallest distance to that query.

A tiny calculation

Let the query be q = [1, 1], with stored vectors A = [1, 2] and B = [4, 5].

distance(q, A) = √[(1−1)² + (1−2)²] = 1
distance(q, B) = √[(1−4)² + (1−5)²] = 5

Therefore A is closer. Euclidean distance (also called L2 distance) is ordinary straight-line distance between vectors.

Why normalize GloVe?

GloVe originally uses angular distance, based on the angle between vectors. The assignment explicitly asks us to use Euclidean distance for all indexes. To preserve the angular ranking, divide every nonzero stored GloVe vector and every query vector by its length. Each normalized vector then has length 1.

For unit vectors x and y:
‖x − y‖² = 2 − 2 (x · y)

Here · is the dot product. Smaller Euclidean distance means larger cosine similarity, so the ordering agrees mathematically. FAISS IndexFlatL2 returns squared L2 distances; this does not change the ordering. Zero vectors need a declared handling rule, and supplied neighbours should be cross-checked after normalization.

03 · Understand the mechanisms

How do the three indexes avoid full search?

HNSW

Graph shortcut. Each vector connects to nearby vectors. Search starts at an entry node, follows promising links, then explores locally.

Build: M (graph links), efConstruction (build search effort).

Search: efSearch (how many candidates to explore).

Cost: Graph links use memory; wider search increases work.

IVF-Flat

Cluster shortcut. Group vectors into coarse buckets using learned centroids. At query time inspect the nearest buckets, then compute exact distances inside them.

Build: nlist (number of buckets).

Search: nprobe (buckets inspected).

Cost: Real nearest neighbour might be assigned to a bucket you skipped.

IVF-PQ

Cluster + compression. Choose buckets as in IVF. Then represent each stored vector with compact codes for pieces of the vector, instead of full 32-bit floats.

Build: nlist, PQ sub-vectors m, bits per code.

Search: nprobe.

Cost: Can lose accuracy even when the correct bucket is searched because distances are approximate.

MethodWhy neighbours may be missedWhat higher search effort doesApproximate storage per vector
Exact FlatNone, apart from floating-point/tie detailsNo approximation knob4 × d bytes
HNSW-FlatGraph search does not explore the right pathHigher efSearch explores more nodes4d + ~8M bytes plus overhead

IVF-PQUnprobed cluster or compression changes rankingHigher nprobe fixes only some errorsm bytes for 8-bit PQ + 8-byte ID, plus codebooks

These are FAISS guide approximations, not measured on-disk sizes. The assignment requires actual index size and bytes per vector. For PQ, m must divide the dimension: 16 works for 128-dimensional SIFT, but not for 100-dimensional GloVe.

05 · Most important correctness check

Recall@10 — and why ties matter

For each query, the exact system returns 10 true nearest neighbours. The approximate system also returns up to 10 IDs. Recall@10 is the fraction of those 10 answer slots filled by acceptable true neighbours.

recall@10 = (number of distinct acceptable retrieved IDs) / 10
dataset recall@10 = mean of per-query recall@10

7 of 10 found → recall@10 = 0.70

This is a toy example, not an experimental result. The real function must also handle distance ties, invalid IDs, and duplicate predictions.

The tie at rank 10

Suppose the true 10th neighbour has a squared L2 distance of 4.0, but another stored vector, ranked 11th by ID tie-breaking, also has distance 4.0. If ANN returns the 11th one instead of the 10th, that is not a mistake. Both are equally close to the query.

A robust implementation establishes the exact 10th-neighbour distance threshold for each query, then checks the actual distances of the 10 distinct returned candidates against that threshold, with a clearly documented small floating-point tolerance. Invalid/duplicate IDs do not earn extra credit. Unit tests must check: perfect result, zero overlap, swapping a tied boundary item, duplicates and invalid IDs.

# Conceptual scoring rule (not copied benchmark code):
threshold = exact_squared_l2_distance_of_10th(q)
acceptable = distinct valid returned ids satisfying
             squared_l2(q, stored[id]) <= threshold + numeric_tolerance
recall_at_10 = min(len(acceptable), 10) / 10

Check your FAISS exact top-10 answers against the HDF5 reference neighbours. Document disagreements caused by near-ties, normalization, or numerical precision. Do not silently assume the HDF5 ordering is identical after normalization.

06 · How to make a trustworthy comparison

What you must actually measure

QPS means queries per second. If one-query-at-a-time search takes 2 seconds for 2,000 queries, throughput is 2,000 / 2 = 1,000 QPS. This example is arithmetic, not a predicted FAISS speed.

  1. Use one machine. Record CPU, RAM, operating system, FAISS version, hnswlib version (if used), BLAS/thread settings, and dataset size.
  2. Run a tuning sweep. Try several HNSW M and IVF nlist choices; for each, sweep efSearch or nprobe from low recall to about 0.95 or above.
  3. Measure one query at a time, on a single thread. Warm up, time repeated trials, record their median, and avoid disk I/O or build time inside the query timer.
  4. Choose settings using only the first 5,000 queries. Freeze choices and produce final recall/QPS on the last 5,000.
  5. Report build cost. Time training + adding vectors where relevant, serialize each index to measure bytes, and compute bytes / number of indexed vectors. State whether training is counted separately.
Do not compare batched exact QPS with unbatched ANN QPS as though they are the same workload. Part 1 separately asks for exact one-by-one versus all-query batch timing. Batching exploits vectorized math and reduces per-call overhead; it answers a throughput question, not the interactive one-query latency question.

Practical recommendation: query difficulty

It reuses the already-built GloVe indexes and directly tests whether one overall recall number hides failures for hard queries.

A possible pre-registered hypothesis: “Queries whose nearest and later neighbours have similar distances will have lower ANN recall than queries with a clear distance gap.” Define the difficulty statistic first; form bin thresholds on tuning queries only; keep bins fixed for the final queries. If the evidence contradicts the hypothesis, report that.

This is a suggested experiment and a theoretical expectation—not a measured finding.

08 · Part 4

Create your own controlled failure case

Part 4 asks a different question from Part 3. Generate or transform vectors yourself. Use at least two of HNSW, IVF-Flat, IVF-PQ. Change one property at a time, use one unchanged control plus at least three changed settings, and keep the generator seeded and at or below 500,000 vectors.

Suggested study: cluster imbalance

Question: Does a growing imbalance in cluster sizes make IVF search less predictable than graph search?

Control: Several well-separated synthetic clusters, with similar numbers of vectors in each.

Variable: Change only the fraction of vectors concentrated in the largest cluster—for example, 25%, 40%, 60%, 80%—while holding dimensionality, total N, noise scale, query method, seeds, and search settings fixed where possible.

Compare: HNSW and IVF-Flat (optionally IVF-PQ), using recall@10, QPS, and errors by cluster. Also measure cluster occupancies so you can test the proposed mechanism.

Hypothesis to commit first: “As cluster sizes become more unbalanced, IVF bucket scanning cost and/or recall at a fixed probe budget may become less uniform; HNSW may respond differently because it uses graph links rather than fixed buckets.”

Important caveat: A fixed nprobe and a fixed QPS target are different controls. Report which comparison you use. Clustering behaviour is learned, so this hypothesis may be wrong.

Why this could matter: A headline “95% recall at X QPS” can hide an uneven failure mode for one group of queries. This is a testable hypothesis, not an assumed result.

Give Part 4 one main figure and at most one page in the report: change, observation, explanation, hypothesis verdict, and what remains untested.

09 · Minimal reliable implementation plan

Build in this order, not all at once

  1. Repository skeleton and evidence log. Write README.md, requirements.txt, hypothesis.md and basic paths. Save AI prompts and responses from the beginning.
  2. Data loader and exact baseline. Read HDF5; map IDs; normalize GloVe; use FAISS IndexFlatL2; validate stored neighbours and recall unit tests.
  3. One dataset + three index types. Start with a small SIFT subset, verify train/add/search; implement one shared timer and CSV row schema.
  4. Quick full-path rehearsal. Run bash run_all.sh --quick on a laptop-sized subset, reproduce each small figure/table in under 15 minutes.
  5. Full benchmark on one pinned machine. Run both datasets, parameter sweeps and repeated single-thread timings; freeze hyperparameters using tuning queries.

The five report questions in simple English

  1. At 95% recall, which index is fastest on SIFT and on GloVe? Does the winner change?
  2. How expensive are construction and memory? What does PQ gain, and what accuracy does it lose?
  3. What did both experiments reveal that overall benchmark numbers could hide?
  4. With 150,000 or 10 million vectors, a 100 ms query budget, and 16 GB RAM, what would you deploy? Use your exact timings and justified scaling assumptions, not a guess.
  5. Give two reasons your benchmark may mislead and say whether you actually tested them.

At 10 million vectors, 128 float32 dimensions alone require about 5.12 GB for raw coordinates (decimal GB), before ID maps, indexes, temporary arrays or the process. That is a storage arithmetic fact, not a measured latency estimate. Explain the RAM headroom and workload of any proposed design.

11 · Be able to explain it yourself

Six questions an evaluator could ask

  1. Why can increasing nprobe improve IVF-Flat recall, but still not fully repair IVF-PQ recall?
  2. Why is HNSW usually more memory-hungry than IVF-PQ? What exactly is being stored?
  3. Why should GloVe base vectors and queries be normalized before L2 search?
  4. How can a correct exact top-10 have a different ID than the HDF5 top-10 without being wrong?
  5. What would make a 2,000 QPS measurement unfair or misleading? Why compare on one machine and one thread?
  6. What evidence from your own CSV, plots and Git commits supports the mechanism claimed in Parts 3 and 4?
Study target: For every plot, be ready to say “what changed, what stayed fixed, what was measured, why it happened, and what I did not test.”
