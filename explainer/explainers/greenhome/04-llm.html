Chapter 04 / LLM & query flow

The LLM does not calculate

From a natural-language request to verified JSON, homeowner confirmation and grounded answers.

Based on actual submitted codeNo invented model capabilitiesOffline reading

Correct the model name first

There is no Gemma model in the frozen main branch. Text processing defaults to qwen3:4b through local Ollama, with deepseek-r1:7b as a fallback. An optional, separate vision model defaults to qwen3-vl:4b; its local inference was reported unavailable in the final verified environment.

Two different LLM workflows

Path A: understand homeowner words

Parse → check → confirm

The text model proposes a strict JSON object describing known home facts, requested measure additions/removals, a ranking objective and budget. The server checks that each proposed fact is supported by direct wording. The customer approves changes before numerical recomputation.

Path B: answer a question

Recompute → select facts → render

The server recomputes the score and current retrofit scenario. The text model only selects up to six allowed fact IDs. Fixed code templates render the factual explanation using actual engine numbers.

User asks“Our loft is poorly insulated. What if we improve it?”

The local language model is a bounded semantic interface, not a free-form agent performing external research, giving eligibility decisions, or generating numerical energy predictions.

Concrete query → concrete structured output

Say this into the app's text entry (not speech-to-text):

“We have a gas boiler, poor loft insulation, single glazing and no smart controls. Explore loft insulation and smart controls under £2,000 to lower our bills.”

Expected type of parsed proposal:
{
  "proposedChanges": {
    "heatingType": "gas_boiler",
    "insulation": "poor",
    "glazing": "single",
    "smartControls": false
  },
  "addMeasures": ["loft", "smart"],
  "removeMeasures": [],
  "objective": "bill",
  "budget": 2000,
  "needsConfirmation": true
}

This is an illustrative supported schema instance, not a captured response to the exact sentence. The parser can omit a field if exact wording or grounding checks do not support it. Roof condition, loft presence and electrical readiness remain unknown until separately confirmed.

What the server checks: only allowed field names and values; no negative budget or unsupported retrofit; assertions rather than hypothetical work; negations (“no solar”) versus installed facts (“has solar”); conflicts with direct-rule extraction; direct text evidence for any LLM-added fact. Every parsed proposal requires homeowner confirmation.

What the LLM is allowed to produce

Fact vocabulary

11 allowed topics

score, baseline, energy, carbon, bill, cost, measures, assumptions, evidence, property_value, funding.

Example answer construction

Not invented prose

When the model selects ["energy","carbon"], the server formats the engine's exact electricity/gas changes and sourced carbon calculation. It does not pass through model-generated numbers or unrestricted prose.

Request: "What if we add a heat pump?"
  parse  → proposed retrofit heatPump
  review → explicit customer confirmation
  model  → simulateScenario(property, selectedIds, options)
  facts  → Qwen chooses ["energy", "carbon", "assumptions"]
  text   → server renders those engine-backed fields

Is it actually multimodal?

Partially prepared, not validated in the final local run. The API accepts up to 5 MB of JPEG/PNG/WebP and supports four narrow output labels: possible visible panels, possible roof damage, possible single-pane glazing, or no clear clue. A returned observation becomes a tentative suggestion that the homeowner must confirm. The final checked environment reported no available installed vision tag, so photo preview is supported but successful vision inference cannot be claimed for that run.

Very important for the live pitch

Never show a photo preview and describe that as proof the vision model detected a leak. The code explicitly disallows diagnosing structural condition from an image. If judges ask, say the visible photo workflow is an extension and the core numerical product does not depend on it.
