BM25: watch k1 and b change a score

Purpose: choose documents that match the important terms in a query from earlier clicks. Example: a user previously clicked “World Cup final”; terms from that title become a query for fresh articles.

BM25(D,Q) = Σ[t ∈ Q] IDF(t) · tf(t,D)·(k1+1) / [ tf(t,D) + k1·(1−b + b·|D|/avgdl) ]

D = article, Q = query words, tf = count of this word in D, |D| = document length in tokens, avgdl = mean length. IDF rewards rare words.

Your A1 default: k1 = 1.2, b = 0.75
Interpret the sliders

k1 = 0: one occurrence nearly saturates the term-frequency reward. Increasing k1 makes repeated appearances matter more.

b = 0: do not penalize long documents. b = 1: full length normalization. At default 0.75, longer documents need more occurrences to earn the same match score.

Why an inverted index?

Example: football → [(article 4, tf=3), (article 8, tf=1), ...]. For a short query, read just the posting lists of its words.

Approximate work: proportional to the total lengths of the query-word posting lists, plus Top-K selection. Not a full scan of every token of every article.

What can go wrong? Popular query terms have huge posting lists; inconsistent tokenization between building and querying; empty histories; stale index; mixed English/Danish stemming.

Measured benchmark: warm-cache sequential p50/p95/p99 = 3.13 / 6.20 / 10.13 ms, throughput 287.44 requests/s. The calculator uses 3.48 ms as an approximate inferred mean, NOT a separately reported measured mean.

Why is measured p99 not the sum of component p99 values?

Each component reaches its 99th percentile on potentially different requests. On one request, candidate generation may be slow but feature extraction fast; on another, the reverse. Sum per-request stage times first, then calculate its percentile.

Submitted A2 report Section 5. Illustrative $0.50/hour cost and 100 ms SLA are not actual vendor prices or production guarantees.

Explain a 10× case without hand-waving

10× traffic: 287.44 → 2,874.4 requests/s. An ideal linear model calls for about 10 equivalent replicas, but repeated index/feature memory, cache warming, traffic skew and coordination can dominate.

10× corpus: float32 vectors alone multiply roughly 10×: N × d × 4. ANN build cost and retrieval time need new benchmarks; they need not scale linearly in query latency. BM25 posting counts track term distribution and corpus size; popular terms can generate enormous posting lists.

10× candidates per query: feature-construction and tree-prediction work may increase about 10× if each candidate must be scored. This is distinct from ten times as many stored articles.

Latency budget: keeping a p99 below 100ms on a warm sequential test does not prove performance under 10× concurrent load. Report queueing and memory bottlenecks.

LightGBM interview answers

Why GBDT instead of a big transformer? It efficiently mixes numerical, categorical and missingness signals and is cheap at per-candidate inference; it does not require expensive online text encoding.

Why LambdaRank? Ranking losses use the set of candidates for a query and emphasize ordering relevant items, commonly with nDCG-aware gradients.

Hyperparameters to recognize: learning rate controls step size; number of trees controls capacity; num_leaves and max_depth control tree complexity; feature_fraction/bagging affect sampling and overfit; early stopping checks held-out quality.

Failure: a good ranker cannot fix positives excluded by retrieval; time-leaky popularity falsely boosts metrics.

Paired bootstrap: resample the same users/requests for both conditions, compute each resampled difference and report a 95% interval. If it excludes zero, there is evidence of a difference under that sampling setup.

Formula sheet — pronounce symbols aloud

Recall@K (candidate recovery)
Recall@K = number of relevant clicked articles retrieved in Top K / number of relevant clicked articles eligible

Example: 3 clicked relevant articles, only 2 in Top 100 → Recall@100 = 2/3. Not the same as the fraction of all retrieved results that are relevant (precision).

AUC (positive-vs-negative pair ordering)
AUC = [#(positive score > negative score) + 0.5×#ties] / (#positive × #negative)

Example: One clicked item beats 3 of 4 non-clicked items → AUC = 0.75. If all candidates have the same label, impression AUC is undefined; state your evaluator's convention.

MRR (first correct answer vs multi-positive variant)
MRR = mean over impressions of 1 / rank_of_first_relevant_item

Example: first click at rank 4 → RR=0.25. Caution: your A1 baseline evaluator reports a MIND-style mean of reciprocal ranks over relevant items, while the literal A2 report defines first-click reciprocal rank. State which harness you're discussing.

DCG and nDCG@K (good clicks early)
DCG@K = Σᵢ₌₁ᴷ (2^relᵢ − 1) / log₂(i+1) ; nDCG@K = DCG@K / IDCG@K

Binary clicks: rel is 1 or 0. Ideal DCG puts every relevant item first. Example: clicking a rank-1 article helps more than clicking rank 10.

Beyond-accuracy: diversity, novelty, coverage
Category diversity = (#Top-10 article pairs with DIFFERENT categories) / (#Top-10 pairs) Novelty = mean(−log₂ smoothed historical article probability) Coverage = #distinct recommended articles / #eligible catalog articles

These are your reported definitions. Higher diversity means less category repetition. Higher novelty favors historically uncommon articles; coverage measures catalog reach. Popularity statistics must use earlier allowed data.

Bootstrap confidence interval
For each bootstrap draw b: sample same impressions/users with replacement; Δᵇ = metric(improvedᵇ) − metric(baselineᵇ). 95% CI = quantile(Δᵇ, [0.025, 0.975])

Why paired? A hard user stays hard for both systems; matching reduces noise. Repeated impressions from one user can motivate user-cluster bootstrap.

Little's Law / utilization
N = X·R ; Xᵢ = Vᵢ·X ; Dᵢ = Vᵢ·Sᵢ ; Uᵢ = X·Dᵢ ; Rᵢ = Wᵢ + Sᵢ

N = average in-flight items, X = throughput per second, R = average response time; V = visits per request; S = active service time per visit; D = service demand per request; U = busy fraction; W = queue wait.

Closed shoppers quiz: R = N/X − Z
N = X·(R+Z) ⇒ R = N/X − Z = 1000/200 − 4.8 = 0.2 seconds

Boundary including user thinking has cycle time R+Z. Server-only boundary has N_server=X·R. Assumption: stable flow with fixed shopper population and negligible other idle time.

B+-tree vs LSM quiz arithmetic
B+ write amp ≈ 4096/120 = 34.13×; 300 writes/s × 4096 bytes = 1.2288 MB/s. LSM: 300 × (1024 bytes appending + ~10×1024 compaction) ≈ 3.38 MB/s, if “further 10×” means additional compaction writes.

A B+-tree rewrites a 4 KB page for each 120-byte price change. The LSM writes more total bytes under the stated model but mostly sequentially. An append-only click log is naturally LSM-friendly. Compare disk access pattern as well as write bytes.

A. Assignment identity, labels and splits

1. Is A2 predicting the A1 objective? What is the y column?

Yes, same recommendation problem, different role of the labels. The objective is to rank news by click likelihood. In A1, observed clicks principally evaluate BM25/semantic retrieval and its resulting ranking. In A2, binary label or y (1=clicked, 0=not clicked) trains the re-ranker. category is a separate input such as Sports, not the answer.

Exposure caveat: your literal A2 open-catalog code sets label=int(candidate_id in clicked). Retrieved but not clicked articles may have never been exposed to the user. Their zeros are weak/unverified negatives. On given impression lists, logged unclicked articles are exposed negatives.

B. Algorithms — with precise distinctions

4. BM25 — can you show me an exact World Cup demo?

Index each article's title + abstract. An inverted index maps each word to the articles containing it and their within-article counts (term frequency).

ArticleDocument text (toy)BM25 for query “world cup final”
N11world cup final argentina0.7828
N12world cup semifinal match0.2836
N13world cup final world cup final0.9381

Why N13 wins: the relevant term “final” appears twice, but its advantage saturates instead of growing linearly. “Final” is rarer than “world” and “cup”, so its IDF contribution is larger. Longer documents are length-normalized. These three scores follow the exact code formula with k1=1.2, b=.75, 3 toy documents and average document length 4.667 tokens.

score(D,Q) = Σt∈Q IDF(t) · [tf(t,D)(k1+1)/(tf(t,D)+k1(1−b+b·|D|/avgdl))]

k1: controls how quickly repeated occurrences stop adding much value. b: controls document-length normalization (0=none, 1=full). Your actual defaults are 1.2 and .75.

5. Are we averaging the last ten World Cup matches/documents?

No for BM25. Your build_user_query() takes the five most recent clicked articles' titles, concatenates them into one text query, and the A2 vectorized BM25 scorer retains up to eight highest query_frequency × IDF terms. It scores each candidate document separately and sorts the scores. It does not average the scores of the last ten matches or the documents.

Different operation: your A1 semantic retriever takes at most ten clicked-article vectors, mean-pools them and normalizes. Your A2 cosine feature can use a recency-weighted average of up to 20 history vectors when embeddings exist. Three different windows; do not mix them.

7. What is HNSW?

Hierarchical Navigable Small World: an approximate nearest-neighbor graph with sparse upper layers and denser lower layers. Search descends from broad entry points to increasingly local neighborhoods instead of comparing the query against every article vector.

Your FAISS index used M=32 (graph connection budget), efConstruction=160 (construction effort), and efSearch=128 (search breadth). Raising efSearch commonly improves ANN recall but increases search latency. Its MIND index used 65,234 × 100-dimensional vectors and serialized to 43,848,922 bytes. This HNSW measurement is separate from the literal A2 BM25-first serving benchmark.

8. What is NRMS?

Neural News Recommendation with Multi-Head Self-Attention. It learns article representations from news text, uses multi-head self-attention to capture relationships, and attention over earlier clicked news to build a learned user representation. A similarity score between user and candidate news gives a ranking. It is not BM25 and is not the 40-tree LightGBM literal reranker.

Your A2 reproduced matched NRMS baselines, then improved one feature: category affinity on MIND, publication freshness on EB-NeRD. Each improvement was selected on calibration data and evaluated on a separate matched set.

9. What is LambdaRank?

Learning to rank within each impression. LightGBM sees feature rows grouped by impression, with labels 1/0. LambdaRank uses pairwise ordering corrections weighted by their effect on an information-retrieval objective such as nDCG. The output is a relative ranking score, not necessarily a calibrated click probability.

Toy impression: N11 clicked=1, N12=0, N13=0. If the model puts N11 below N12, a pairwise ranking correction favors moving N11 above N12. The same features can be used to compare models fairly because the candidate list and labels remain fixed.

10. Which algorithm actually produced my A1 leaderboard results?

MIND A1 submission 900266: SpeedyRec/UniLM base neural relevance scores + nine engineered features → LightGBM reranker (AUC .7197201 in the verified handoff).

EB A1 submission 905893: serving-safe P1/F LightGBM LambdaRank, 238 features, best iteration 376 (actual AUC .7959300). The displayed EB rank was affected by duplicate score rows; an auxiliary beyond-accuracy tail was deliberately post-processed. The A1 controlled baselines were simpler BM25 and semantic/FAISS-HNSW experiments; they should be reported separately from the leaderboard extensions.

MIND recency: earlier history positions decay with a five-item half-life because exact click times are unavailable. EB recency: time-based half-life of seven days. Note that the literal first stage excludes history IDs; so history_repeat will normally be 0 for those retrieved candidates. It still has meaning as a feature definition for other candidate pathways.

14. What is the temporal guard or behavioral-window boundary?

The system may only use evidence that existed before the impression. For a request at 10:05, a user click at 09:59 can enter history, but a click at 10:07 must not. Frozen popularity must come from an earlier training prefix; EB candidates with known publish time later than request are filtered. Without this guard, training sees future behavior and overstates quality.

Code: _causal_history() rejects click timestamps greater than or equal to the impression time; the pipeline asserts chronological fit/validation separation.

15. Why are tied timestamps updated only after the entire group?

Toy example: the same user has two requests stamped 10:00. Suppose I101 clicked sports article N11, while I102 is also timestamped 10:00. If you update the history immediately after processing I101, I102 improperly learns I101's click even though both events have the same recorded time and no trustworthy order.

Correct two-pass rule: at timestamp 10:00, compute all requests' features using state from before 10:00; only afterward apply their observed outcomes for timestamps later than 10:00. Your _session_counts() uses a pending update buffer for this reason.

16. What do frozen training-prefix popularity and CTR mean?

Popularity: number of earlier clicks for an article. In your literal A2 code, it is counted using only the frozen pre-fit training prefix; a smoothed probability is (article_clicks+1)/(all_prefix_clicks+catalog_size). For example, 20 earlier clicks → train_prefix_popularity=20. It is not necessarily CTR.

CTR = click-through rate: clicks / logged displays (impressions). Example: 20 clicks among 100 exposures → CTR=0.20. Counts are not sufficient to compute CTR without an exposure denominator. Your high-scoring A1 MIND extension had a separate smoothed_item_ctr_alpha50 feature; do not mislabel A2's prefix click count as CTR.

17. What are dual availability indicators and what do missing values mean?

Value + missingness flag. Two pairs in your literal pipeline are (freshness_hours, freshness_available) and (history_mean_dwell, history_dwell_available). If publication time is unavailable, freshness_hours=0, freshness_available=0; if known and exactly just published, freshness_hours=0, freshness_available=1. Without the flag, those two cases would look identical.

MIND lacks per-history click timestamps, dwell time and article publication timestamps in the literal adapter. Unavailable fields are not silently treated as true zeros.

18. How is a user represented?

A1 BM25: a text query concatenating up to five eligible history titles. A1 semantic: mean of up to ten L2-normalized clicked-article vectors, then normalize; FAISS inner product acts as cosine.

Literal A2: a feature profile (history length, categories, recency-weighted affinities, previously clicked IDs, session state); if article embeddings exist, a weighted history vector (up to 20 recent clicks) supplies a candidate cosine feature. NRMS: learns an attention-weighted user vector from clicked news. There is no single universal user representation across your experiments.

D. Paired metrics, latency and scaling

19. What is paired metric comparison and a paired bootstrap CI?

Evaluate baseline and improved models on the very same impression IDs, then form per-impression differences and resample the paired units with replacement. When the same user appears repeatedly, cluster by user where that is the declared protocol. A 95% interval excluding 0 supports a nonzero average gain under that bootstrap procedure.

Literal MIND: AUC BM25 .64268 → reranked .62647; difference −.01620, CI [−.09011, .05259]: does not demonstrate an AUC gain.

Literal EB: AUC .63317 → .86830; difference +.23513, CI [.17055, .29722] among impressions where conditional AUC exists. However candidate recall remains poor.

Separate matched NRMS study: MIND category affinity gain ΔAUC .03577 CI [.02717, .04466]; EB freshness gain ΔAUC .00706 CI [.00456, .00961]. These use 10,000 user-clustered bootstrap draws. Do not mix their test sets with the literal pipeline.

20. What exactly is being timed when we profile latency?

In the literal MIND serving benchmark, the timer surrounds one request: (1) BM25 top-200 retrieval, (2) lookup/build 15 feature columns, (3) model prediction, (4) sorting into final order. Article preprocessing, initial BM25 index build, original dataset loading and model training happen before the timed request. The test ran 2,000 warm-cache held-out requests in a loaded local process.

Reported end-to-end p50/p95/p99: 3.13 / 6.20 / 10.13 ms. Component p99: candidate generation 1.13 ms, feature builder 6.52 ms, tree prediction 4.96 ms. Do not add the component p99s: their worst 1% of requests may be different.

21. What are latency, throughput, scale and sequential serving?

Latency: elapsed time for one request to receive a ranking (ms/request). Throughput: completed requests per second (QPS). Scale: ability to maintain target latency and throughput as request traffic, catalog vectors or user-history/log size grows. These three growth variables are different.

Sequential: the benchmark issues the next request only after the prior request finishes; one loaded process is used. The model can still use native computation threads—this is not a single-CPU-thread test. It measured 287.44 requests/s; that is not proof of 287.44 QPS under concurrent production traffic.

22. What is p99? What does 287.44 QPS tell us?

p99 = 99th-percentile latency: roughly 99% of tested requests finish at or below this duration; around 1% are slower. On 2,000 measured requests, about 20 are in the slowest 1%. Here p99 was 10.13 ms.

Throughput: completed_requests / benchmark_wall_time. For a sequential server, observed 287.44 QPS implies around 1000/287.44 ≈ 3.48 ms per request on average, broadly consistent with p50=3.13 ms. Do not invert p99 to estimate QPS; use the mean/full wall-clock measurement.

23. What fails first at 10×, and does this benchmark prove the SLA?

10× traffic: roughly 2,874 QPS; naive linear replication suggests ~10 identical servers if nothing else changes, but queueing, cache contention and shared storage may make this optimistic.

10× catalog: vector+graph memory and ANN/index build grow; lexical postings and feature data grow; search costs may change. 10× history/events: temporal joins, prefix aggregation, and memory pressure grow. Your measured feature-construction p99=6.52 ms suggests focusing optimization there.

Your local sequential p99 <100 ms satisfies the example local target, not a validated concurrent production SLA. The $0.50/hour and $0.000483/1000 queries figures are an illustrative cost model, not a real bill.

24. What is ranking's final difference between A1 and A2?

Controlled A1: compare BM25 and semantic scores on candidates/retrieve the clicked news. Literal A2: BM25 top 200 → learn to reorder using 15 behavioral/content features → test baseline vs reranked on identical candidates.

Important failure: MIND 4,904/5,000 validation requests and EB 4,916/5,000 had zero recovered clicks among top 200. A2 MRR/nDCG on full catalog retrieval are tiny because the relevant item is absent. A sophisticated reranker cannot recover items that were never retrieved.

Final submissions: MIND A2 uses a distinct FAST15–SpeedyRec residual system, while EB A2 reuses A1's P1/F. So do not assert your final A2 leaderboard uses the literal 40-tree reranker.
