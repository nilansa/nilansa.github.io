1. Show the postings list

A1 · src/ire_a1/bm25.py:34–51 · direct excerpt
postings: dict[str, list[tuple[int, int]]] = defaultdict(list)
for doc_idx, text in enumerate(texts):
    counts = Counter(tokenize(text))
    doc_lengths[doc_idx] = sum(counts.values())
    for term, tf in counts.items():
        postings[term].append((doc_idx, tf))
self.postings = dict(postings)
self.idf = {
    term: math.log(1.0 + (n_docs - len(items) + 0.5)
                             / (len(items) + 0.5))
    for term, items in self.postings.items()
}

Interpretation: a postings list maps a word to articles containing it. Each pair holds a doc_idx (which article) and tf (how many times that word occurs there).

Tiny example: "cat" → [(0,2), (4,1)] means the word cat appears twice in article 0, once in article 4. A term absent from that list needs no score computation.

Why use an inverted index rather than scanning all articles?

A full scan compares every query term against every document. With an inverted index, you traverse only the posting lists for terms in the query. Frequent terms may still have long lists, and Python dictionaries/lists cost RAM; therefore the index isn't free.

What did you use from libraries, and what was handmade?

Handwritten: tokenizer, posting construction, Robertson BM25 scoring, top-K corpus heap selection. Libraries: Python Counter/defaultdict, heapq, math, re, and NumPy for arrays. This is not Elasticsearch, Whoosh or Pyserini doing the actual BM25 work.

2. BM25 formula and parameters

One query term contributes approximately IDF × normalized term-frequency, and the code adds contributions across terms.

score(t,d) = IDF(t) × tf(t,d)(k1+1) / [tf(t,d) + k1(1−b+b·|d|/avgdl)]

In your implementation, query-term count multiplies each term score, and IDF uses log(1+(N−df+.5)/(df+.5)).

Higher k1 lets repeated mentions provide more additional score; lower k1 saturates sooner.

b=0: ignore article length. b=1: fully normalize against average length.

What if b=0, k1=0, or a query term is rare?

b=0 removes document-length penalty. Small positive k1 makes term-frequency saturation fast. Higher IDF makes rare words count more. Rare named entities and breaking-news labels are a strength of lexical matching.

Why normalized inner product? If both article and user vectors have length 1, their dot product equals cosine similarity. Why HNSW? It uses a navigable graph to avoid an exact comparison with every stored vector, trading memory and occasional misses for query speed.

HNSW parameters: M / efConstruction / efSearch

M=32: number of graph links per node (approximately; implementation-specific). Larger M generally improves connectivity/recall but raises index memory/build cost. efConstruction=160: breadth of neighbor exploration during index building; higher usually improves graph quality and build time. efSearch=128: breadth during querying; larger usually improves recall but increases latency. These are not LightGBM hyperparameters.

Why is a user mean vector imperfect?

It blends separate interests into one direction, e.g., half football and half politics. Recent relevant clicks may be diluted by older/unrelated interests. An empty or entirely uncovered history gives None, followed by a zero-score fallback in candidate scoring.

Difference from A1: A1 full-corpus retrieval defaults to up to 32 query terms; this literal A2 implementation keeps 8 IDF-weighted terms and precomputes NumPy postings weights. The underlying BM25 formula remains k1=1.2, b=0.75. A2 fills low-recall lists using a fixed training-prefix popularity order, while keeping causal article eligibility.

Explain the index optimization in 20 seconds

Instead of repeating scalar BM25 term-frequency arithmetic per query/article, preprocessing calculates document-term scores once, stores arrays of posting IDs and scores, and adds vectorized slices to a score array. This trades index/build memory for faster repeated query scoring. Accuracy must be tested after optimization because tie handling and floating-point operations can change.

What is group? A list of impression sizes, such as [100,100,200]. This tells LightGBM which candidates compete with one another inside each user impression. Training optimizes relative order, not independent click classification.

LightGBM

A library that learns an additive ensemble of decision trees. Each new tree corrects ranking errors of the current ensemble. n_estimators=40 sets the number of trees; learning_rate=0.08 scales each correction.

LambdaRank

A learning-to-rank objective: it uses pairs of candidate documents within a query/impression to push relevant items above less relevant ones, with an emphasis related to ranking quality such as nDCG. LambdaRank is the objective; LightGBM is the library.

Parameter viva: what happens if num_leaves, depth, learning rate, trees change?

More num_leaves or max_depth allows complex interactions but raises overfitting/cost risk. More boosting trees adds capacity and training/inference work; lower learning rate often needs more trees. min_child_samples discourages tiny overfit leaves. group is not a hyperparameter: it defines each impression's ranking unit.

Two tiny worked examples you can explain aloud

MRR

Ranked labels: [0,1,0,1]. The first relevant article is in position 2: A2 first-hit reciprocal rank = 1/2. A1 average-over-positives definition instead gives (1/2 + 1/4)/2 = 0.375.

AUC

Scores: clicked article 0.8, unclicked 0.2 → AUC 1.0. Swap the scores → AUC 0. If scores tie, the pair contributes 0.5. AUC doesn't measure index size or retrieval speed.

What if all impression candidates have identical click labels?

There are no clicked/unclicked pairs to compare, so AUC is undefined (A1 returns NaN; A2 returns None in that evaluator). Do not silently treat this as AUC = 0.5 unless a separately declared competition scorer explicitly does so.

Why must bootstrap sample complete impressions or users?

Candidate rows within one impression share the same query, history and exposures, so they are not independent. Paired experiments must resample the same impressions in both arms to estimate the difference. Repeated users justify cluster resampling. Catalog coverage is a set union, so A2 uses equal-sized distinct-request batches to avoid replacement-occupancy bias.

Show exactly how A2 computes ranking metrics

A2 · src/ire_a2/evaluation.py:264–304 · selected functions
def _ranking(scores, top_k):
    return np.argsort(-scores, kind="stable")[:min(top_k, len(scores))]

def _mrr_from_ranking(labels, ranking):
    ranked_labels = labels[ranking]
    positives = np.flatnonzero(ranked_labels == 1)
    return 0.0 if len(positives) == 0 else 1.0 / float(positives[0] + 1)

def _ndcg_from_ranking(labels, ranking, k, observed_positive_count=None):
    ranked = labels[ranking[:k]].astype(np.float64)
    discounts = 1.0 / np.log2(np.arange(2, len(ranked) + 2))
    dcg = float(np.sum(ranked * discounts))
    positives = int(np.sum(labels)) if observed_positive_count is None else observed_positive_count
    ideal_length = min(k, positives)
    idcg = float(np.sum(1.0 / np.log2(np.arange(2, ideal_length + 2))))
    return 0.0 if idcg == 0.0 else dcg / idcg

Why is observed_positive_count supplied? If retrieval misses 3 out of 4 clicked articles, computing ideal DCG using the single retrieved positive would overstate ranking quality. The numerator only includes retrieved items, but the denominator knows what was actually clicked.

Two measured bottlenecks to explain

Quality failure: candidates not recovered

Your literal A2 run had 4,904/5,000 MIND requests and 4,916/5,000 EB requests with no clicked item retrieved. A perfect ranker cannot fix an item that never enters top-200.

Engineering failure: recomputing embeddings

Your A1 report describes a cold-cache EB MiniLM run that encoded 47 batches and spent ~148 s before terminating. Caching reusable embeddings moves this work offline; the interrupted run does not justify claiming a quantified speedup.

10×: Which resource fails first?

If impressions grow by 10× while the catalog stays constant, per-impression CPU/feature work and streaming I/O dominate; processing time grows roughly 10× if throughput is unchanged. If catalog vectors grow by 10×, HNSW/vector memory and query cost also grow; neither scales exactly from raw float32 bytes. Online scaling additionally needs replica RAM, cache locality and concurrent P99 load tests.
