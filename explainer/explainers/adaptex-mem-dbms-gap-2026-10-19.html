ADAPTEX-MEM: Find the failure before inventing an index

A database-systems perspective on agent memory: what has already been solved, which bottlenecks could remain, and how to test whether adaptation is actually worth its cost.

1. What are we trying to improve?

An AI agent can store facts from previous sessions. Retrieval decides which stored facts are shown when the agent asks a question. A static pipeline uses the same retrieval settings for every query. An adaptive pipeline selects settings based on the query and workload.

InterpretEntity / time / semantic signals

MergeRank and trim to k
MeasureDid evidence appear in top k?

What is the datum?

A memory record: text, owner, timestamp, entities, source and possible update/version.

What is an index?

An auxiliary data structure for finding candidate records without scanning everything.

What is a query planner?

A rule or model choosing which index, order and depth to use for this query.
Correction to the original proposal: A Bloom filter cannot safely prove that no semantically relevant memory exists unless the queried key and filter's membership semantics are well-defined. HNSW is approximate and has no universal O(log n) retrieval guarantee. B+ trees help with structured ranges, not semantic meaning. Treat these as candidates, never automatic upgrades.

3. Tight research problem

Proposed question: For a changing corpus of timestamped agent memories, when does query-conditioned selection of existing retrieval mechanisms outperform the best fixed configuration under equal evidence budget, latency and maintenance constraints?

Let q be a query, M a memory corpus, c a retrieval configuration (for example, keyword versus hybrid retrieval), R(q,c) evidence recall at top k, and C(q,c) its measured cost.

Best fixed: max over c of mean_q R(q,c) Oracle upper bound: mean_q max over c R(q,c) Adaptation headroom = Oracle − Best fixed Practical goal: maximize recall subject to p95 latency, write cost, index memory and query-time budget.

Important: The oracle knows the answer after evaluation; it is only a diagnostic upper bound. A real router must generalize to unseen queries and pay for its own inference. Never present oracle recall as deployable performance.

H1 · Non-uniform failures

Different query classes prefer different retrieval decisions; no global setting consistently dominates.

H2 · Learnable selection

A lightweight selector approaches the oracle advantage on held-out sessions, not only training questions.

H3 · Net benefit

Any recall gain survives full accounting for routing, building, updating and maintaining indices.

4. Interactive intuition: one size might not fit all

Select a query type. These invented numbers are a teaching illustration, not measured results. Different strategies can win for different query types.

A production system needs calibrated query features, a fallback path, and a cost comparison—not an oracle label.

5. A disciplined experiment ladder

  1. Build a fixed, reproducible corpus and gold evidence labels. Use a small BEIR dataset to debug scoring; use LoCoMo / LongMemEval for agent-memory claims, honoring session boundaries and evidence IDs.
  2. Strong cheap baselines first. BM25 or FTS, simple dense search, RRF hybrid, timestamp/entity metadata; same k and candidate budget. Separate retrieval-only Recall@10/15 from answer accuracy.
  3. Change one component at a time. Query rewriting, depth, hard/soft filters, reranking, routing, or index family; freeze everything else. Log where candidate pools differ but final Recall@k does not.
  4. Measure headroom before training. Best global static configuration versus per-query oracle. Bootstrap by session or conversation, not by correlated individual questions alone.
  5. Train the smallest controller justified by headroom. Compare static, simple heuristics, logistic routing and learned routing on held-out conversations and shifted query distributions.
  6. Account for costs. Include ingestion/write amplification, index build, memory size, controller overhead, p50/p95 latency, throughput and cost per retrieved evidence item.
Stop/go rule: If best static hybrid search already matches adaptive recall within uncertainty—or the router costs more than its benefit—report that negative result. It rules out needless architectural complexity.

Where custom data structures could become necessary

Only after evidence of a specific missing operation: a repeated temporal+semantic join, fast version conflict resolution, cross-agent provenance lookup, or an update pattern where existing indices violate measurable latency/storage limits. Then compare composition against a strong DBMS query plan—not only against a flat vector store.

6. First measured baseline: small lexical-only pilot

On 19 October 2026, a CPU-only run evaluated 1,973 evidence-labelled LoCoMo questions from 10 conversations (5,882 dialogue turns) included in the Memory-Benchmarks archive. Index units were one dialogue turn; retrieval used speaker and text only. This is a descriptive sanity check, not a paper-grade agent-memory result.

Fixed retrieval or upper boundEvidence Recall@10Recall@15
BM2554.59%58.25%
TF-IDF53.04%56.69%
Reciprocal Rank Fusion54.06%57.29%
Per-query oracle (not deployable)55.56%58.93%

The strongest fixed lexical baseline is BM25. The oracle gains only 0.97 percentage points at Recall@10, with a 10-conversation cluster bootstrap interval of approximately 0.53–1.38 points. Thus choosing among these similar lexical approaches offers limited potential gain here. This does not test dense retrieval, metadata filters, graphs or learned routers, and it does not justify broad claims of equivalence.

Interpretation: This is a valuable negative control. Do not spend weeks training a lexical router unless a more diverse retrieval decision set gives much larger headroom. The pilot excludes 13 questions with absent or unresolved evidence labels, evaluates original dialogue IDs, and performs no end-to-end language-model answering.
