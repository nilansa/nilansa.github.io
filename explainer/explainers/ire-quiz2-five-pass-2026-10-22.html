Six latency and load ideas

01 · Utilisation cliff

80% busy is not 20% safe.

Bursts form queues as capacity fills. Slowest users suffer first.

Median steady, p99 doubles at 80% CPU.

Do: Add serving headroom; target roughly ≤70% utilisation.

02 · Little's law

Slower replies mean more requests waiting.

At unchanged arrival rate, longer response time means more work in flight.

A pause triples latency; thread pool fills although CPU is low.

Why: About 3× more requests are in flight.

03 · Bottleneck

Speed up the busiest stage.

Replicating an idle front end does not help a saturated compute stage.

Photo processor is slow; preprocessing server is idle.

Do: Add capacity at the photo processor.

04 · Tail at scale

Parallel calls wait for the slowest one.

More partitions mean more chances that one runs slowly.

A dashboard fans out to 300 shards; p99 gets worse.

Why: One slow shard delays the overall response.

05 · Batch vs serving

Batch wants full use. Serving needs spare room.

Background jobs on live nodes can cause long request delays.

Weekly compaction makes the API slow.

Do: Throttle it or move it to a separate pool.

06 · Offline vs online

A better score can give users a worse product.

Offline relevance judges quality; online use includes speed and abandonment.

Better snippets double page-load time.

Do: Evaluate user impact and latency, not relevance alone.

Five consistency and storage ideas

07 · Read-your-writes

After an edit, show the writer the new value.

Other users may temporarily see an older value if that is acceptable.

Fix: Give the editor a fresh/consistent read after their write.

08 · CAP during a partition

Be strict for money; tolerate stale browsing.

If regions cannot communicate, bookings must not silently contradict each other.

Choice: Reject unsafe writes; stale hotel listings may be acceptable.

09 · PACELC / locality

Put the write leader close to the writer.

Remote coordination adds latency even when no network partition exists.

Choice: Keep each user's primary record near the home region.

10 · RUM trade-off

No free read + update + memory win.

Index design improves some costs at the expense of others; workload matters.

Trap: Reject claims of universal superiority on all three.

11 · Bloom filter

“Not present” is reliable; “present” may be a lie.

A probabilistic membership filter can report a false positive.

Trap: Blocking on a filter alone may block an innocent user.

Five additional IR ideas to recognise

  • Zipf: Few terms are very common; most are rare. Posting list sizes are uneven.
  • Heaps: Vocabulary grows as more text is indexed, even very late.
  • Inverted index: Store each term → sorted list of documents containing it.
  • Compression: Store document-ID gaps; read fewer bytes at the cost of decoding.
  • MinHash / banding: Estimate near-duplicate similarity; compare candidate pairs, not every pair.

Mark when you can explain these without looking

Quick check: why isn't 80% CPU safe?

Average utilisation hides bursts. Queueing grows sharply near full utilisation; p99 often increases before mean latency becomes alarming.

Quick check: why can more shards worsen p99?

Each shard may be faster, but a fan-out request waits for all mandatory responses. A single rare straggler delays the user.

Quick check: Bloom filter says “not in set” — can it be wrong?

No, for a standard Bloom filter with no deletions and correctly executed inserts. A “present” answer can be a false positive.

PASS 2 · READY · 20–30 MINUTES

Understand the mechanism, not just the name

Use these three questions for every situation: What is slow or stale? Why does it happen? Which change fixes the cause?

1. Capacity is not the same as responsiveness

Utilisation cliff

Meaning: utilisation is the fraction of available serving capacity in use. An average of 80% does not mean a request always finds a free worker.

Example: 10 counters can handle 10 tasks per second. Nine requests arriving at once still queue, even if the average is only eight per second.

Why p99 worsens first: a small fraction of unlucky requests hits a queue. The median can appear fine.

Wrong fix: “Wait until CPU reaches 100%.” The harm starts earlier. Better: headroom, load-shedding or scaling.

Little's law

Meaning: requests currently in a stable system = requests completed per second × seconds each spends there.

Example: if arrivals stay fixed and an internal pause triples each request's response time, three times as many requests occupy connections or threads.

Important contrast: low CPU does not imply free threads. A blocked request still occupies a worker.

Wrong fix: add CPUs when the real issue is threads blocked on a pause. Better: remove the pause, bound waiting or provide enough concurrency safely.

2. Find the actual resource that limits throughput

Path through a service: client → preprocess → expensive inference → result. Each query visits the cheap service once and one of three inference replicas.

Service demand and bottlenecks

Service time (S): time a resource spends on one visit. Visits (V): average visits to that resource for one request. Demand (D = V × S): total resource work per completed request.

Maximum throughput is bounded by the largest effective demand, considering the available replicas. If inference uses nearly all its CPU and preprocess is idle, add inference capacity.

Why a replica helps only sometimes

One replica can split load across servers. But copying the wrong stage leaves the bottleneck unchanged. More cache nodes also cannot rescue an overloaded database if every request still hits that database.

Question cue: “Which server should be replicated?” Look for high demand, high utilisation or long queues at that exact stage.

3. More parallel work can increase end-to-end waiting

Tail at scale

Fan-out: one user request invokes many independent back-end tasks. Straggler: one slow task. If the response requires every result, a straggler controls the finish time.

Example: A page queries 300 data shards. The typical shard is fast. One unlucky shard can still make the whole page slow.

Wrong claim: “Each shard got faster; so the total p99 must improve.” Faster average shards do not eliminate the multiplication of straggler chances.

Batch versus serving

Batch: finish a lot of work at high utilisation; individual tasks may wait. Serving: meet a latency objective; maintain spare capacity to absorb bursts.

Example: compaction uses spare CPU during normal traffic, then flash-sale traffic arrives. API queues form.

Better: use a separate pool, isolate resources, throttle background I/O or schedule heavy merges in quieter periods.

4. Correctness and speed depend on the operation

CAP: partition-aware choices

Partition: two network regions cannot communicate reliably. Availability: accept and respond to requests. Consistency: preserve a single coherent view for the relevant operation.

Hotel example: displaying an old list may be acceptable. Confirming the last available room twice is not.

Reason by invariant: stale reads may be fine; irreversible conflicting writes need stronger consistency or temporary rejection.

Read-your-writes

Async follower: a read replica that catches up after the leader. Read-your-writes: a user must see their own completed update in later reads.

Example: you update your avatar, refresh the page, and see the old avatar. Route your own subsequent reads to a replica that has applied the write.

Wrong fix: force every user worldwide to use synchronous reads when only the writer needs immediate freshness.

PACELC and locality

During a partition: trade availability against consistency. Else: coordination still trades latency against consistency. Even healthy regions incur long round trips.

Example: fitness records are edited mostly from the owner's home city and read by friends elsewhere. Placing the write leader near home reduces write latency.

Wrong fix: place the master near the largest count of passive readers if low-latency owner writes are the critical requirement.

RUM: a workload-specific trade-off

R: read overhead. U: update overhead. M: memory/storage overhead. Structures choose where to spend resources.

Example: maintaining extra indexes helps reads but costs memory and updates. Buffering writes helps updates but creates extra read/merge work.

Beware: the source specifically rejects claims of universally winning on all three across all workloads.

5. Probabilistic answers need verification

Bloom filter

Stores a compact set-membership summary. Each inserted key sets several bits. A query checks those bits.

If even one needed bit is zero, the key was not inserted (under standard assumptions). If all bits are one, unrelated keys may have set those bits.

Safe application: skip a disk lookup after “definitely absent”; verify against the source of truth after “possibly present.”

Offline versus online evaluation

Offline: judged relevance on an existing test set, such as precision, recall or NDCG. Online: real latency, user interaction and abandonments.

Example: a new summariser improves relevance but adds seconds to every page. Offline quality rises; the user experience falls.

Better: track both search quality and end-to-end user cost. Do not accept an algorithm solely because one offline metric rises.

6. General IR concepts: recognise the design implication

Why Zipf matters for serving

Term frequency is highly skewed: a few words occur in many documents and have huge posting lists. Process rare terms first for an AND query, cache hot terms, and avoid scanning every occurrence of “the”. Source: Module 2, pages 7 and 29.

Why Heaps matters for building an index

Vocabulary keeps growing with the number of tokens, including product IDs, typos and error codes. A scalable dictionary is needed; vocabulary is not “finished” after the first large batch. Source: Module 2, page 8.

Why an inverted index is fast

Instead of scanning every document for “earbuds”, look up earbuds → [doc 1, doc 2, doc 3]. An AND query intersects posting lists; a phrase query also checks positions. Source: Module 2, pages 25, 26 and 29.

Why compression can make queries faster

Sorted document IDs have small gaps. Compressing those gaps reduces I/O and may more than offset CPU decompression time. This is a compute-for-bandwidth trade. Source: Module 2, page 31.

Why shingling, MinHash and LSH go together

Shingles convert documents to sets. Jaccard measures the overlap of sets. MinHash estimates that overlap with small signatures. LSH banding selects likely matches without comparing all document pairs. Source: Module 2, pages 10–16.
