Simple difference: Retrieval asks which articles deserve consideration? Ranking asks in what order should we show them?

BM25 — the actual mechanism

Every document is a news title plus abstract. postings["cricket"] = [(doc7,2),(doc21,1)] means “cricket” appears twice in document 7 and once in document 21.

k1=1.2: how quickly repeated terms stop adding much score. b=0.75: how much long documents are penalized. IDF: rare words count more.

A1 full-corpus retrieval keeps up to 32 informative terms; the literal A2 source keeps up to eight IDF-weighted terms and precomputes posting weights as NumPy arrays.

Semantic — the actual mechanism

MIND uses mean-pooled 100-dimensional TransE entity vectors. EB-NeRD uses cached 384-dimensional multilingual MiniLM embeddings. User representation is the normalized average of up to ten recent, valid clicked-article vectors.

FAISS IndexHNSWFlat stores a neighbor graph. Search follows edges rather than comparing everything. M=32 controls graph connectivity, efConstruction=160 construction breadth, and efSearch=128 query-time breadth. nprobe is an IVF parameter, not HNSW.

LightGBM and LambdaRank — don't confuse them

LightGBM is the library that trains gradient-boosted decision trees. LambdaRank is the objective for improving the relative order of articles inside each impression. group=[100,200] means the first 100 candidate rows belong to one impression and the next 200 to another.

Your literal A2 implementation uses 40 trees, learning_rate=0.08, num_leaves=15, max_depth=6. The higher-scoring EB-NeRD leaderboard model is a different 238-feature model.

Why did the baseline fail to retrieve positives?

News interests can involve multiple topics. A query formed from a small history sample may not include terms or meanings related to the next click. A two-stage system cannot rank what stage one never provided. Improve candidate recall or merge lexical and semantic sources before making stage two more complex.

What features helped the learned EB model?

Not one magic embedding. Its feature families cover article age/freshness, user history, category and entity overlap, multi-window popularity, time-of-day, session and exposure counts, and within-impression score transforms. These signals explain why the final learned model is not a fair one-to-one comparison with the A1 content-only baselines.

Q1(b) — derive the answer aloud

1000 shoppers total

Think + wait + receive results

→
200 queries/second

Throughput X

→
4.8 seconds thinking

Z

Let N be average shoppers in the closed system, X be completed queries per second, Z be thinking time, and R be response time.

Whole system includes thinking: N=X(R+Z). Only the server: average in-flight requests N_server=X·R. In the closed system, R=N/X−Z=1000/200−4.8=5−4.8=0.2 seconds.

Assumption: steady-state flow balance with a fixed population and average throughput. Do not say “Little's Law is always CPU utilization.” It is about average items, throughput and average time.

Q1(c): page rewrites and amplification

B+-tree: 120 bytes logically change, but a whole 4096-byte page is rewritten. Write amplification 4096/120 ≈ 34.13×. Device write rate 4096×300≈1.23 MB/s (decimal MB).

LSM: append whole 1KB record and then roughly another 10× compaction writing (under the question's wording): about (1+10)×1024×300≈3.38 MB/s. If the instructor treats “10× write amplification” as inclusive, explain your interpretation. The LSM may be attractive for large append streams, but compaction can create substantial write amplification.

Choice: catalogue has point lookups and updates, so a B+-tree can be defensible in this toy calculation. High-rate append-only click logs favor an append/LSM-oriented design. State read/write workload, memory, disk I/O and compaction costs.

Part A: System / model anatomy

Q1. What changed from A1 to A2? Draw it.

A1: BM25 postings or FAISS article vector search retrieves candidates based on content. A2: A1 BM25 top-200 → 15 past-behaviour/content features per candidate → LightGBM LambdaRank → final order. We add personalization and news freshness, not a new ground-truth label.

Q2. What is the training row, label and group?

Each row represents one (impression, candidate article). The label is 1 if the candidate was clicked, otherwise 0. The group sizes tell LightGBM which candidate rows belong to the same impression, so LambdaRank compares articles within a request.

Q3. Explain five feature families and when they are available.

BM25 retrieval score/rank, user history length/category affinity, recency-weighted affinity, historical popularity, and article freshness. The code also uses repeat, earlier-session clicks, dwell-availability and embedding cosine. All behaviour and popularity must be from before the scored impression.

Q4. How do you prove no future click leakage?

A1 uses a chronological split and explicit history boundary tests. In A2, _causal_history() rejects timestamps at or after the impression. _session_counts() computes same-timestamp features before updating state. Popularity uses an earlier training prefix, not validation or test clicks.

Q5. Explain num_leaves, max_depth, learning rate, and tree count.

The literal A2 model has 15 leaves, max depth 6, 40 trees, learning rate .08. More leaves/depth let the tree model fit more interactions but risk overfitting and cost. More trees add compute; a lower learning rate often needs more boosting rounds. These are not HNSW graph parameters.

Q6. Is the 238-feature EB leaderboard model the literal 15-feature model?

No. The literal A2 pedagogical pipeline has 15 features/40 trees. EB hidden-test 905893 reuses the earlier P1/F 238-feature LightGBM LambdaRank with deeper session/popularity/interaction features. Keep model identity separate from baseline experiments.

Part B: Engineering measurements

Q7. If the TA points at FAISS and asks memory size, what do you measure?

Raw vectors need N × dimension × bytes-per-coordinate. The serialized index file also stores graph links/metadata. RSS is resident physical memory of the whole Python process, including other arrays, models and libraries. Total machine RAM is system capacity. The A2 report separately measures MIND HNSW serialized size 43,848,922 bytes.

Q8. p99 = average of 99 out of 100 requests, yes?

No. p99 is a latency threshold at which roughly 99% of observed requests are at or below that time. The slowest ~1% exceed it. It is not the average of 99 observations. p50 is the median. A2 end-to-end p50/p95/p99: 3.13/6.20/10.13 ms.

Q9. Why do stage p99s not add up to overall p99?

The request with slowest BM25 retrieval need not be the request with slowest feature generation or model scoring. To measure end-to-end p99, record each request's full time, then compute the 99th percentile of those totals.

Q10. Throughput in impressions per second: what does it count?

One impression is a user context plus candidates that must be retrieved/scored/ranked. Throughput counts complete requests finished per second. A2's measured 287.44 requests/s came from 2,000 sequential warm-cache MIND requests. Do not call it a concurrent production stress test.

Q11. How is your serving time measured in source?

A2 benchmark_literal_serving.py:98–145 uses time.perf_counter_ns() around retrieval, features, prediction and sorting. It computes each stage in milliseconds and p50/p95/p99 with NumPy quantiles.

Q12. What if request traffic goes 10×? What if catalog size goes 10×?

10× requests stress per-request CPU, feature build, queues, replica capacity, tail latency and output writing. 10× catalog increases vocabulary/postings or vector/index storage, offline build cost and retrieval search time. At 287.44 req/s current benchmark, 10× requests ≈ 2,874.4 req/s. Ten equivalent replicas is only a rough linear capacity model; not proof of production behaviour.

Q13. Estimate cost per 1,000 impressions.

Use (machine dollars/hour × 1000)/(queries/second × 3600). With illustrative $0.50/hour and 287.44 req/s: $0.000483 per 1,000 requests. This excludes many real hosting costs, idle capacity and concurrent bottlenecks; report it as illustrative.

Part C: Functional results / evaluation

Q14. Can the second-stage ranker fix missing clicked articles?

No. The ranker can reorder only retrieved candidates. The literal A2 run missed all clicks on 4,904 of 5,000 MIND validation requests and 4,916 of 5,000 EB requests. Improving candidate sourcing is the first quality priority.

Q15. What is the evidence that your one-feature NRMS change helped?

MIND add category affinity: AUC .58163 → .61740, paired difference +.03577 with 95% CI [.02717,.04466]. EB add seven-day freshness: .68991 → .69697, difference +.00706 with CI [.00456,.00961]. Both CIs exclude zero. The comparison uses the same candidates and a held-out evaluation set.

Q16. What if your MIND literal A2 AUC decreases?

Say so: .64268 → .62647 with 95% CI for the delta [−.09011,.05259] including zero. It is not a statistically supported improvement. Correct measurements and analysis matter more than claiming every model improved.

Q17. How did you compute AUC, MRR, nDCG and diversity?

Code implements these with NumPy. AUC averages clicked-vs-unclicked pair ordering (ties get half credit). A1 MRR averages reciprocal ranks over all clicked items; A2 literal MRR uses the first clicked item. nDCG discounts lower positions, normalized by ideal ordering. Diversity is the fraction of top-ten category pairs that differ.

Q18. Why a paired, user-clustered bootstrap?

To compare two systems fairly, evaluate the same requests under both and resample paired units. When users repeat, resample user clusters so a user's impressions stay together. A2 matched NRMS CI uses 10,000 user-clustered resamples.

Q19. Why did you not use candidate source position as a feature?

Source order was not a randomized exposure experiment and may reflect logging or earlier ranking biases. Using it could falsely reward data collection artefacts rather than true relevance. The A2 literal report explicitly says it excluded original position from serving features.

Q20. What are cold/warm and head/tail slices in A2?

Cold means user unseen in earlier training data; warm means seen. Head-history means at least one historical article had 5+ earlier training-prefix clicks; other histories are tail. These are defined before final evaluation to test where a system behaves differently.

One 10× scaling formula

If a single loaded process handles 287.44 impressions/s sequentially, then a 10× traffic rate is 2,874.4 impressions/s. Under a simple perfect-scaling assumption, roughly ten equivalent replicas would maintain the old throughput. This is only a capacity estimate. Shared disk/cache bottlenecks, burstiness, duplicate state, contention and p99 can invalidate it.

Different 10×: if you increase article catalog size instead of request rate, RAM for vectors/postings and retrieval latency may become the bottleneck even without more users.
